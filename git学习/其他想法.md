# 工具只是手段
 Git 不仅仅是背命令，把 add、commit、rebase、stash 敲熟不一定就学好了。命令只是基础，重要的是开发规范：什么时候新建分支、一次提交改多少内容、提交信息怎么写、哪些改动不应该提交、团队里哪些操作不能做。同样是完成功能，杂乱无章的提交历史和清晰有序的历史，后续排查 漏洞、回滚版本的效率差距很大。Git 是用来管理变更的，不是单纯用来上传代码的
# 区分 个人开发和 多人协作规则不同
自己一个人写项目的时候，自由度很高，reset、rebase、强制推送都可以随便试，出问题自己用 reflog 找回就行。但一旦进入团队协作，规则立刻变严格：公共主分支不能随便 rebase，两套模式不能混在一起，很多冲突、代码丢失事故，都是把单人习惯带到团队里造成的。这也让我意识到，写代码不只是实现功能，还要兼顾和其他人的配合
# 命令行和图形工具各有价值，不用排斥其一
Git Bash 命令行上手门槛高，但能看清发生了什么，每一步改动都由自己控制，排查奇怪问题的时候更有底气。图形工具操作简单，适合日常快速提交。不能只会点按钮，底层逻辑一无所知，遇到报错就无从下手
# 还有很多内容值得持续深挖
这次学习覆盖了常用进阶操作，但还有很多场景没有深入：比如 git hook 自动校验提交、CI/CD 结合 GitHub 自动构建、大型仓库的性能优化、复杂冲突的沟通处理。Git 上手容易，精通很难，短时间只能掌握高频用法，想要熟练应对复杂项目，需要长期在项目里反复实践。
# 踩坑也是一种学习
学习过程中难免出现推送失败、代码冲突、误删提交等问题。一开始遇到报错会慌乱，慢慢发现报错信息本身就是提示。遇到问题不要急于喂给AI
经验和思维是AI无法代替的
